# 旅行 Agent 产品画像

Sep 28, 2026 · @The lucky few

## 一句话定位

帮信息不对称的旅行者更快决定「去哪、何时去」。卖的不是攻略,是跨语言的信息差套利:把中英文社区的真实经验综合起来,用母语给出有据可查的决策建议。

## 目标用户

核心用户是中文用户里的 P 人:随性、不爱做行程表,但常被随性反噬,比如到门口才发现要预约、错过末班车。

- **P 人旅行者**:产品替他们承担 J 人的角色,而不是把他们改造成 J 人。
- **跨欧亚旅行者**:海外华人或常在欧洲和亚洲之间旅行的人,两边的信息都需要。创始人本人就是第一个用户。
- **女性独行视角**:作为可展开的视角,不单独做产品。用户勾选「女生独行」时,卡片展开独行友好度、夜间出行建议、住宿区域建议;此刻模式守住末班车等回程约束。

## 核心差异化

三点共同构成护城河,任何一点单独都容易被复制。

1. **跨语言信息差**:综合小红书、Reddit、Wikivoyage 的内容,用母语输出。中英文社区意见冲突时不裁决,直接呈现「两个互联网的不同看法」。
2. **决策层,不是执行层**:回答「去哪、何时、有没有平替」。竞品在目的地框输入「喜欢自然」只会做字面匹配,这是空白位置。
3. **替 P 人当 J 人**:只规划不可逆的事(要预约的、要抢票的),其余留白。

## 四个关键时刻

产品陪用户走完一次旅行的四个时刻,每一步都不要求用户做 J 人的事。

收藏箱攒久了本身就是一张欲望地图:agent 可以反过来发起决策对话,比如「你存的格鲁吉亚内容最多,十月正是最佳季节」。路线只按区域聚类给「菜单」,不给时间表。

## MVP 范围

MVP 只证明一件事:用户愿不愿意用它做旅行决策。核心链路是:

1. 偏好输入(预算、时间、出发地、想体验什么)
2. 目的地卡片(匹配理由带来源、时间窗口、预算、观点分歧、不可逆事项)
3. 收藏
4. 过几天回来继续比较
5. 生成目的地简报

前端先用网页(当前是 Streamlit),不急着做原生 App。首页是决策入口,不做资讯推荐流。

验证标准:创始人拿一个真实纠结去问,得到的答案比自己刷两小时小红书更好;再找约 20 个真实用户试用。

## MVP 暂缓、后续规划

以下功能都要做,只是排在核心链路验证之后。顺序原则:越依赖已有能力、越强化差异化的越靠前;越重、越接近竞品主场的越靠后。

| 顺序 | 功能 | 做法 |
| --- | --- | --- |
| 1 | 旅行日记 | 用照片时间戳和定位自动生成路线与时间线,用户零输入 |
| 2 | 社区 | 同时作为语料来源,用户经验经同意后进入知识库;有几百个真实用户后再做 |
| 3 | 排线与地图 | 从区域菜单延伸,选定几个点后再排顺序和交通时间;先做导出到其他行程工具 |
| 4 | 多人协作 | 先做轻量的「分享卡片让朋友投票」,不做实时协同编辑 |
| 5 | 订票闭环 | 商业化路径最清晰(佣金),之前用跳转链接替代 |
| 6 | 短视频 | 成本最高、离核心能力最远,最后评估 |

## 竞品格局

执行层已经很拥挤,产品卡位在它们的上游,而不是正面竞争。

| 产品 | 类型 | 主要能力 | 对我们的意义 |
| --- | --- | --- | --- |
| 圆周旅迹 | 中文执行层 | 一键导入小红书攻略、自动排线、交通耗时、行程地图、多人协作 | 排线护城河很深;目的地框只能做字面匹配,决策层空白 |
| Gooh 旅记 | 中文执行层 | AI 规划、攻略库、小红书笔记解析、AA 记账、行李清单、Citywalk 轨迹、离线可用 | 印证「粘贴链接解析」已是标配,只能当数据入口 |
| Mindtrip | 英文 AI 规划 | 聊天内预订、实时价格 | 只支持英文,覆盖不到中文信息 |
| Layla | 英文 AI 规划 | 对话式规划、接入比价平台 | 同上 |
| Wanderlog | 英文执行层 | 地图可视化、协作规划 | 执行层功能成熟 |

可以和执行层工具共存:用户在这里决定去哪、何时去,再导出到圆周旅迹或 Gooh 排行程。

## 产品红线

- **有据可查**:每条推荐理由必须能追溯到具体来源,禁止 LLM 凭常识空写。来源少时如实显示「置信度有限」。
- **安全判断从严**:宁可说「信息不足」,也不说「很安全」。安全字段在没有足够独立来源时不给结论。
- **内容合规**:对外部社区内容做综合和归因,附原文链接,不整段转载。不大规模爬取有反爬限制的平台,改用用户主动粘贴或查询时实时搜索。

## 技术现状与近期待办

已决定把两套平行规划器合流成一条 RAG 排序主干,LLM 只插在三个增值点上。原则是:过滤和结构用代码,品味用 LLM。

**现状**:仓库里并存 LLM agent 循环(有 key 时的主路径,输出缺引用和评分明细)和 RAG 排序管线(备用路径,输出反而更丰富)。代码已实现 V6 的 chat 端点,但 spec 仍停在 V5。

**合流后的三个 LLM 注入点**:

1. 生成检索查询,结果不佳时改写重查(从普通 RAG 升级为 agentic RAG)
2. 重排序(接入已有的 reranker)
3. 撰写推荐理由,必须引用证据 ID
