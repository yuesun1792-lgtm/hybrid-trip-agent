# Unified planning architecture

This document describes the current runtime. The older architecture review and version
specifications are historical. No LangChain, LangGraph or multi-agent runtime is added.
An optional local MCP place-resolution node is described in [place resolution](place_resolution.md).

## Business contracts

`planning_models.py` defines `TripConstraints`, `PlanningTask`, `Day`, `Activity`,
`RevisionRequest`, `RevisionChange`, `AffectedScope` and `ValidationIssue`.
`models.py` contains API response/evidence/analysis models and keeps `ItineraryDay` as
an alias of `Day` for compatibility. `TripPlan.itinerary` and each day's `plan` text
remain available; the editable business source is `Day.activities`.

An activity has a stable ID, title, description, category, time slot, evidence IDs and
verification status. Place ID, duration and item cost are nullable. Generation cannot
populate those numerical/logistics fields from model guesses. Activities generated by
a model are `proposed`, not verified or confirmed. Rule placeholders are explicitly
`needs_verification`. Stable content-addressed evidence IDs survive local revisions;
run-local labels are no longer used as persistent evidence identity.

## Controlled scheduler

```text
Chat/form adapter
  -> task preparation and prerequisite validation
  -> resolve candidates (known set or bounded discovery)
  -> common overview analysis of every candidate
  -> compare using the same constraints
  -> options output OR detailed research and activity generation for the selection
  -> validate complete plan
  -> commit immutable plan version
  -> language presentation (does not overwrite committed state)
```

`task_builder.py` converts inputs into a common task. Both specified and unspecified
destinations use `destination_analysis.analyze_destination`. Overview analysis reuses
discovery evidence and avoids generating a schedule per candidate. Only selected
cities receive detailed retrieval and full daily activities. `requested_output=options`
returns candidate comparisons with an empty itinerary. Selecting a city in a subsequent
turn can promote options into a full plan.

`unified_planner.py` owns scheduling. The active router uses `plan_trip` for creation regardless of destination presence; legacy intent labels remain accepted for compatibility. Explicit requested output overrides model suggestions. Candidate discovery may ask an LLM for new English
queries, bounded by round/query/candidate limits. It cannot invent candidate facts.
`plan_builder.py` generates 1-3, 1-4 or 1-6 activities per day for low, medium or high
pacing respectively (default: medium). Fewer activities are permitted. Longer trips are generated in batches of at most four days with global day numbers and shared stable evidence IDs; failed batches are explicit fallbacks rather than silently dropping days. Pacing is a count
limit, not a verified time/transport feasibility guarantee.

If RAG is absent, curated city names seed the same analysis pipeline. If the model,
credentials or evidence are unavailable, the shared builder produces clearly marked
placeholders; it does not fall through to an independent planner. A confirmed city is
not silently replaced when its estimated cost exceeds budget: a visible budget warning
is returned. Discovery excludes known over-budget candidates and asks for changed
constraints if none remain. Unknown costs remain null.

## Revisions

Creation and revision share analysis, activity generation, rendering and validation.
Revision adds preparation, dependency scope and merge nodes:

1. Validate base plan ID/version and parse explicit IDs or a day/time-slot request.
2. Calculate affected activities and explicitly preserved IDs.
3. Reuse existing evidence; research only when replacement/addition needs new activities.
4. Generate only affected days/time slots; different days retain different requirements.
5. Merge replacements with untouched records. Unchanged activity IDs and content remain
   identical. Replacements receive new IDs. Remove/relax operations need no generation.
6. Revalidate the entire plan and commit the next version only on success.

Creation forwards free-form user requirements (e.g. named stops) to the builder in addition
to normalized constraints. Local generation caps replacement count by the affected records
plus explicit add operations, preventing protected activities from being regenerated as extras.

Destination, duration, date, origin, transport, global interests and pacing corrections
trigger broader reanalysis. Budget-only changes recheck estimates without rewriting
activities. A local food/shopping change does not alter global interests. Ambiguous
requests wait for clarification; pending proposed constraints stay separate from the
committed plan. Numeric answers can fill known pending fields. Contradictory preservation
(e.g. keep a Paris activity while changing the destination to Rome) requires clarification.

Supported operations are replace, add, remove and relax. Complex callers can supply
`ChatRequest.revision` with structured changes instead of relying on natural-language
heuristics. Unspecified or invalid targets are not clamped to an arbitrary day.

## Validation and commit

`plan_validation.py` checks consecutive day numbers, dates, confirmed destination,
unique IDs, activity presence/count, evidence existence/city, excessive known duration,
preservation and estimated budget issues. It reports unknown logistics. Citation IDs
are attached to each activity and citation; final references are built from activity
references. JSON/schema success does not prove factual entailment, venue opening hours,
travel connections or real-world suitability. Such facts still need trusted live tools.

`plan_store.py` provides a repository protocol and an in-memory implementation with
optimistic version checks and deep-copy snapshots. One conversation serializes its turns;
independent conversations can run concurrently. Stale `expected_plan_version` returns
HTTP 409 before expensive calls. Validation failures do not commit a draft. Read canonical
latest/history with `GET /plans/{plan_id}` or `?version=1` without an LLM call.

This is single-process storage: restarting the server loses conversation/plan history,
and multiple workers do not share it. Trajectories persist to disk but are diagnostic
logs, not execution checkpoints. A durable repository/checkpointer is a separate adapter
for a future persistence or LangGraph integration.

## Tools, budgets, language and trace

`tool_executor.py` validates registered read-only tools, accounts for calls and returns a
common result/error envelope. Local retrieval and mock transport currently use it.
The place-resolution node uses a separate bounded stdio MCP adapter with the same shared
run budget/trajectory context. It discovers two approved tools backed by real Geoapify,
and resolves only new activity IDs before validation/commit. External writes and approval
policies are not implemented. The deprecated Anthropic agent/tool loop remains available for
historical callers and tests but is not used by the HTTP planning endpoints.

`execution.py` holds a per-run context: deadline, tool/LLM call counts and conservative
maximum-output-token reservations. Limits are checked before calls; LLM timeouts are
capped by remaining time. These are cooperative admission limits, not a cancellation
engine for CPU work or an exactly enforced monetary budget. SDK internal retries remain
bounded separately. Default frontend wait is 180 seconds.

Internal names, categories and source data stay canonical English. Chinese input uses
English retrieval; the committed activity model remains separate from language rendering.
`language.py` translates prose and display slot labels while retaining IDs, constraints,
prices, dates, enums, URLs and original evidence. Compatibility day text is regenerated
from translated activities. Translations never become the baseline for the next revision.

Trajectory records task preparation, candidate resolution/analysis, tool execution,
structured generation, revision scope/merge, validation, commit and translation, together
with budgets, typed inputs/outputs, errors and provider usage.

## Extension boundary

Future LangGraph integration replaces scheduler/state persistence, not the domain
models, destination analysis, tool executor, merge logic or validator. Individual functions
can become graph nodes; overview and detailed analysis can become subgraphs. Additional
agents should return proposals with evidence and IDs, leaving validated commits under
one owner. MCP supplies tools through adapters rather than bypassing the executor.
